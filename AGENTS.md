# Instructions for AI Coding Agents

Welcome to the **Modbus Workbench** project. This is a zero-dependency, client-side industrial workbench and simulator that executes all Modbus protocol processing and multi-server simulations in the browser using Web Workers, WebSockets, and Web Serial / WebUSB interfaces.

Please adhere strictly to the following architectural guidelines, rules, and design philosophies when editing this codebase:

---

## 1. Zero-Dependency Client-Side Protocol Architecture
- **Pure Client-Side Processing:** There must be **no server-side Modbus processing components**. All Modbus frame construction, cyclic redundancy check (CRC-16) validation, MBAP header assembling, packet decoding, and simulation loop calculations must execute strictly on the client side inside dedicated **Web Workers**.
- **Multi-Server Simulation:** The application must support simulating **multiple simultaneous Modbus server instances**, each connected to distinct endpoints:
  - **Modbus TCP:** Multiple virtual servers connected over independent WebSockets routed to specific remote IP addresses and ports via WebSocket bridges (e.g., `websocat` running on the host bridging WebSocket traffic to TCP).
  - **Modbus RTU:** Multiple serial servers interfacing with physical or virtual adapters via the Web Serial API (`navigator.serial`) and WebUSB interfaces.
- **Unified Partitioned Database:** All simulated Modbus servers must store and retrieve their memory state (`coils`, `discreteInputs`, `holdingRegisters`, `inputRegisters`) and tags within **one central database**, partitioned and distinguished by their unique endpoint identifier (e.g., `IP Address + Port` for TCP, or `COM / Serial Port Number` for RTU).
- **Core Protocol Modules:**
  - `/src/utils/modbusRtu.ts`: Custom binary frame encoders, CRC-16 calculations, and serial transceiver presets.
  - `/src/utils/modbusTcpSimulator.ts`: Pure client-side MBAP packet parsers, request simulators, and memory mapper.
  - `/src/utils/serverPortManager.ts`: Automatic sequential WebSocket port allocation, collision detection, and port reassignment.
  - `/src/utils/circularLogBuffer.ts`: Fixed-capacity ring buffer preventing memory leaks and GC pauses during high-frequency telemetry.
  - `/src/utils/csvTagParser.ts`: CENTUM VP Modbus CSV configuration parser and multi-slave memory mapper.
  - `/src/workers/modbus.worker.ts`: Background Web Worker executing real-time multi-server process ticks, dynamic signal sweeps (Sine, Ramp, Noise), and packet simulations without blocking UI threads.

## 2. Network & Hardware Interfaces
- **Web Interface Hosting (Port 3000):** Port 3000 is reserved strictly for serving the static web client assets (Vite dev / production bundles). No Modbus protocol execution or state authority resides in the HTTP server.
- **WebSocket TCP Bridges (Host `websocat`):** Modbus TCP communication operates via client-side WebSocket connections (`ws://` / `wss://`) connecting out to a WebSocket-to-TCP bridge gateway (such as `websocat` or equivalent bridge proxy running on the host machine connecting WebSocket packets directly to TCP devices).
- **Dynamic Sequential WebSocket Ports for Multi-Server TCP:**
  - Multiple simultaneous Modbus TCP servers must **never** share the same WebSocket bridge port.
  - Each unique Modbus TCP slave endpoint must be allocated a dedicated, sequential WebSocket port starting from `5020` (e.g., `5020`, `5021`, `5022`, ...).
  - All multi-instance bridge scripts (Bash `.sh`, PowerShell `.ps1`, Windows Batch `.bat`) generated by the application must bind each slave to its dedicated port (`ws-l:0.0.0.0:<port> tcp-l:<target_ip>:502`) to guarantee concurrent execution without `EADDRINUSE` port collisions.
- **Web Serial API Priority & WebUSB:**
  - Physical USB-to-RS485 and serial adapter communication prioritizes the standard **Web Serial API** (`navigator.serial.requestPort()`), providing native support for FTDI, CH340, CP2102, Prolific, and Silicon Labs COM port devices, with secondary fallback to WebUSB (`navigator.usb`).
  - Browser permissions block `navigator.serial` and `navigator.usb` when running inside iframes (`window.self !== window.top`).
  - **Iframe Fallback Banner:** Display a prominent top banner in RTU view when running inside an iframe advising users to click **'Open in New Tab'** to connect to physical USB/RS485 serial ports.
  - **Simulator Bridge Mode:** In environments without attached physical serial hardware or inside iframes, the built-in Web Worker simulator must intercept packets, validate CRCs, and return simulated responses.

## 3. UI/UX Style Guide & Industrial Design
- **Industrial SCADA Aesthetic:** Maintain a sleek, dark industrial SCADA workbench theme (`#0a0a0a` background, subtle high-contrast borders, refined typography).
- **Two Primary Headers Layout:**
  - **1. App Header (Global Header):** Houses app-wide controls, including the single **Server Instance Selector** dropdown (e.g., `[ Server: 172.31.28.103:5020 ▼ ]` or `All Servers (Global View)`), Single-Tab Session Status badge (`Active Session` / `Session Inactive (Take Over)`), Telemetry Logging quick status & timer toggle (`Log: Off` / `Log: M:SS`), CSV Config Import trigger, Reset Defaults, Settings & Telemetry Logs navigation, and PWA install prompt.
  - **2. Table Header (Table Toolbar):** Situated directly above tables to manage view category tabs (`Coils`, `Discrete Inputs`, `Holding Registers`, `Input Registers`, `Tag Database View`, `Settings & Logs`) and table-specific search/bank/update-mode filters.
- **Single Server Instance Selector Rule:** There must be no separate or duplicate server dropdown inside the Tag Database view or table toolbar. The Tag Database view and register tables automatically synchronize with the single Server Instance Selector located in the App Header.
- **Port Badges & Collision Resolution:**
  - For Modbus TCP servers, display the allocated WebSocket listening port badge (e.g. `WS :5020`) in the server dropdown and configured server cards.
  - If duplicate WebSocket ports are detected across TCP servers, the UI must render an alert banner detailing the collision and offer a one-click auto-resolve action (`Auto Ports (5020+)`) to reassign sequential ports.
- **Table Column Display Strategy (Server IP / N-S-P):**
  - **Modbus TCP:** Display a dedicated **`Server IP`** column.
  - **Modbus RTU:** Display a dedicated **`N-S-P`** column representing Node, Slot, and Port (e.g., `1-1-1` derived from `K1-N-Sxxxxx` and subsystem port `P`, stripped of leading zeros).
  - **Global View (All Servers):** Dynamically display **`Server IP / N-S-P`** showing the IP address for TCP servers or `N-S-P` for RTU servers.
- **Table Sorting Hierarchy:**
  - All data tables (Registers Table, CSV Tag Database) must be sorted in the following order:
    - **Modbus TCP:** 1) `Server IP Address`, 2) `Hardware Addr` (sorted by base numerical integer offset).
    - **Modbus RTU:** 1) `N-S-P`, 2) `Hardware Addr` (sorted by base numerical integer offset).
- **Alternating Table Row Colors:** All data tables (Registers Table, CSV Tag Browser, Log Screens) must use **alternating row background colors** (zebra striping: e.g. `even:bg-white/[0.02] odd:bg-transparent`) to ensure optimal scan legibility across dense register lists.
- **Color-Coded Byte-Map Chips:** Highlight decoded frame bytes using consistent, high-contrast chips:
  - **Green (`emerald`):** Slave ID / Unit Identifier
  - **Indigo (`indigo`):** Function Code
  - **Yellow / Amber (`amber`):** CRC-16 Checksum / MBAP Header
  - **Neutral / Slate (`neutral`):** Data Payload Bytes
- **Focused Diagnostics:** Keep workflows uncluttered and focused on diagnostic efficiency, real-time value changes, and packet telemetry.

## 4. CSV File Import for Modbus Server Configuration

### 4.1 CSV File Structure & Headers
- **Header Metadata Lines:** Ignore lines 1–4 (metadata starting with `@PRODUCTS`, `@ID`, `@SHEET`, `@DATE`).
- **Column Header Row:** Line 5 contains the column header definitions.
- **Processed Columns:**
  - `@Element`: Hardware word memory address (e.g., `%WW0001`).
  - `Buffer`: Buffer length in words (numeric value on the first row of a buffer, `*` for continuation rows).
  - `Program Name`: ALE communication module identifier in the format `K1-N-Sxxxxx` (where `K1` is a fixed prefix, `N` = node number, `S` = slot number, and `xxxxx` = protocol name, e.g., `K1-1-S01FMODBUS`). Only buffers configured for Modbus protocols (`FMODBUS` or containing `MODBUS`) are imported.
  - `Size`: Block definition size in words (numeric value on the first row of a block, `*` for continuation rows).
  - `Port`: Subsystem communication port number (e.g., `1`).
  - `IP Address`: IP address of the Modbus server station (e.g., `172.31.28.103`). If no IP address is present, the configuration is considered Modbus RTU.
  - `Station`: Station number.
  - `Device&Address`: Device update mode prefix, bank digit, and address in `FDxxxx` format (e.g., `A40001`).
  - `Data Type`: Numeric integer code (1–14) specifying data format and direction.
  - `Reverse`: Word/bit swap flag:
    - Discrete types (13, 14): `1` = Bit-swap 16 bits, `2` = Standard order (no swap).
    - 32-bit types (2, 4, 5, 8, 10, 11): `2` = Swap two 16-bit words (CDAB), `3` = Standard order / no swap (ABCD). (Code `1` is not used).
    - 64-bit types (6, 12): Word swapping is not applied.
  - `Scan`: Scan rate indicator (e.g., `1s`).
  - `Service Comment`: Human-readable signal description.
  - `Label`: CENTUM VP tag name identifier (starts with `%%`).

*All other columns in the CSV file are ignored.*

### 4.2 Hierarchy & Grouping Rules
1. **Buffer Hierarchy:**
   - A configuration file consists of one or more **Buffers**.
   - A buffer begins when a numeric value appears in the `Buffer` column alongside a protocol definition in the `Program Name` column, and spans all subsequent rows marked with `*` in the `Buffer` column until the next numeric value (marking the start of the next buffer) or EOF.
   - **Protocol Filter:** Only buffers that have `FMODBUS` (or `MODBUS`) in the `Program Name` column should be imported. Buffers associated with other protocols (e.g., `PROFINET`, `ETHERNET/IP`, `FOUNDATION Fieldbus`) must be ignored.
   
2. **Block Definition Hierarchy:**
   - Each buffer contains one or more **Block Definitions** beginning with a numeric value in the `Size` column and spanning all subsequent rows marked with `*` in the `Size` column until the next numeric value (where the current block ends and the next block starts) or EOF.
   - Blocks are direct children of their parent Buffer.
3. **Device Definition & Address Scope:**
   - The `Device&Address` column uses `FDxxxx` format, where `F` is the Update Mode character, `D` is the Modbus register bank digit (`3` = Input Register, `4` = Holding Register, `0` = Coil, `1` = Discrete Input), and `xxxx` is the 4-digit decimal base address.
   - A device definition spans all subsequent rows marked with `*` in the `Device&Address` column until the next explicit `FDxxxx` address value (where the current device definition ends and the next begins) or EOF.
   - Within a device definition block, all child elements inherit the values for `IP Address`, `Station`, `Device&Address`, `Data Type`, and `Reverse` from the header row of the device definition.
   - Each device definition contains multiple device elements that span one or more CSV rows depending on their Data Type (e.g., 16-bit Integer = 1 row / 1 word, 32-bit Float / Long = 2 rows / 2 words, 64-bit Double = 4 rows / 4 words).
   - Tags must be created with respect to their Data Types, displaying the address range of the element in short hyphenated format (`0001-2`). For example:
     - 16-bit Integer: Address shown as `0001` (next element at `0002`).
     - 32-bit Float/Long: Address range shown as `0001-2` or `0015-16` (next element at `0003-4` or `0017-18`).
     - 64-bit Double: Address range shown as `0001-4` or `0005-8` (next element at `0005-8` or `0009-12`).
4. **Multi-Word Data Types & Unmapped Register Display:**
   - Data types requiring multiple words (e.g., 32-bit Float = 2 words = 2 lines) span multiple rows. Continuation rows (`*`) inherit parent properties.
   - The CSV parser combines all continuation rows belonging to a multi-word data type into a single tag assigned to the base address and range (e.g., `0001-2`), automatically advancing the starting address of the next element by the word count of the data type (e.g., to `0003`). The same range-based display method must be used across all register tabs (Holding Registers, Input Registers) and the Tag Database tab.
   - **Device Definition vs. Raw Unmapped Registers:**
     - If an unmapped register is part of a 32-bit or 64-bit Device Definition, it must be shown as a hyphenated range (e.g., `0001-2` or `0001-4`).
     - If a register is not part of a multi-word device definition, it must be shown as a standard single 16-bit word (e.g., `0001`, `0002`).
5. **Discrete Registers:**
   - Data types 13 and 14 map each `%WWxxxx` row as a full 16-bit register containing 16 individual status bits.
6. **Gap Rows:**
   - Empty device address rows without service comments are treated as buffer gaps; they advance memory offsets by 1 word per empty row but do not create active tags.
7. **Automatic Port Allocation on CSV Import:**
   - When importing a CSV configuration containing multiple unique `IP Address` entries, each unique host must automatically be assigned an incremented sequential WebSocket port (starting at `5020`) to ensure immediate multi-slave bridge compatibility without port contention.

### 4.3 Update Mode Specifications
The leading character `F` in `FDxxxx` defines the subsystem update & readback mode:
- **`A`**: Read packet in word units; Write designated packet with readback.
- **`B`**: Read packet in word units; Write only changed single bit/word device with readback.
- **`C`**: Read packet in word units; Write only changed single 32-bit register with readback.
- **`X`**: Write packet only once when change occurs (no readback).
- **`Y`**: Write only changed single bit/word device once when change occurs (no readback).
- **`Z`**: Write only changed single 32-bit register once when change occurs (no readback).

### 4.5 Simulation & Signal Generation
- **Initial Mode:** Imported tags default to `constant` mode with baseline values (e.g., `100.0` for analogs, `1` for discrete).
- **Manual Overrides & Static Mode:** Setting any register or generator to **Static** (`mode: 'none'`) forces the tag's `simMode` to `constant`. Manual edits from the UI immediately lock the value to static to prevent background simulation loops from overwriting user-forced values.

## 5. Tag & Register Database Persistence
- **Storage Key:** `modbus_tag_database` (unified database partitioned by server IP/Port or Serial Port).
- **Auto-Persistence:** All tag modifications, server additions, and CSV imports automatically synchronize to `localStorage` (and IndexedDB for multi-server scale).
- **Factory Reset:** "Reset Defaults" restores the baseline factory tag configurations.

---

## 6. Single-Active-Tab Policy & Exclusive Session Authority
- **Strict Single-Tab Execution:** To prevent duplicate simulations, bridge port (`5020+`) collisions, and message queue contention, only **one browser tab** may actively run the background Web Worker, simulation tickers, and WebSocket bridge connections at any time. Multi-tab state broadcasting over BroadcastChannel is replaced by exclusive session authority.
- **Session Coordinator & Heartbeat:** Uses `BroadcastChannel("modbus_single_tab_coordinator")` paired with `localStorage` heartbeats (`modbus_active_tab_id` and `modbus_active_tab_hb`, 1500ms interval) to detect active sessions across browser tabs.
- **Standby State & Takeover Modal (`SingleTabTakeoverModal`):**
  - Opening a secondary tab displays a modal informing the user that another tab is active and holds the new tab in standby.
  - Clicking **"Take Over Active Session"** claims active authority and broadcasts a `TAKE_OVER_SESSION` event.
- **Graceful Session Yielding:** Upon receiving a takeover notice, the previously active tab immediately halts its heartbeat, terminates its Web Worker, closes any open server WebSockets, and transitions to standby with an informative takeover alert.

## 8. Telemetry Logging & Memory Safety
- **Disabled-by-Default Startup:** All packet and transmission telemetry logging is **disabled by default on application startup**. This guarantees zero CPU/memory overhead and prevents background worker message queues from growing during unattended or high-frequency runs.
- **Configurable Auto-Stop Timer:**
  - Logging is activated on-demand with a selectable duration timer (default **5 minutes**; options: 1, 2, 5, 10, 15, 30, 60 minutes).
  - A countdown timer runs in the UI and automatically shuts off logging when it reaches 0:00.
  - Users can manually stop or restart logging at any time from the App Header quick badge or the Live Transmission Terminal.
- **Worker-Side Suppression:** The background Web Worker respects a `SET_LOGGING_ACTIVE` control message. When logging is inactive, `ADD_LOG` events and raw byte extraction are completely bypassed at the source.
- **Fixed Circular Ring Buffer:** All packet logs and telemetry must be stored in a circular ring buffer capped at a maximum of 100 entries (`src/utils/circularLogBuffer.ts`) with $O(1)$ overwrites to prevent memory leaks during long-running sessions.
- **Detached Byte Truncation:** Raw packet byte arrays logged for telemetry must be truncated to a maximum of 32 bytes and stored in detached `Uint8Array` instances so large WebSocket frame buffers are garbage-collected immediately.
- **Throttled UI Updates:** Log additions must be flushed to the React UI via a throttled timer (150ms interval) to prevent UI thread starvation during rapid Modbus polling.
